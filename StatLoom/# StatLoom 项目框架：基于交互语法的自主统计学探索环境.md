# StatLoom 项目框架：基于交互语法的自主统计学探索环境

## 一、项目定位

StatLoom（统计织机）是一个交互式统计学学习工作台。用户导入自己的数据，自主选择分析问题、统计方法与探索方向，在数据、公式、统计量、数学推导和概念之间自由切换。系统通过真实的统计计算、可操作的数学对象和完整的追踪机制，使抽象的统计学知识与具体的数据对象建立联系。

StatLoom 不以固定课程、线性教程或统计计算器为核心形态。它的目标不是替用户规划一条完整的学习路径，而是创造一个能够支持自主观察、操作、比较和追踪的环境，使用户可以从自己的数据与问题出发，逐步发现统计学中的数学关系。

项目在交互设计上借鉴 Terra Faction UI 的方法：视觉身份、布局、控件行为、状态反馈与具体任务相互协调。界面不是静态内容的容器，而是一个能够响应用户操作、反映真实状态并提供进一步探索入口的系统。

StatLoom 将这种设计方法应用于统计学领域，形成自己的交互语法：数据点可以被操作，统计量可以被追踪，公式可以被展开，概念关系可以被探索，分析状态可以被保留和比较。所有视觉反馈都应有明确的对象与计算依据。

## 二、核心设计理念

### 2.1 自主探索，而非预设学习流程

系统不规定用户必须按照什么顺序接触统计学知识，也不要求用户完成指定步骤才能进入其他功能。

用户可以从多个入口开始：

- 从数据出发，观察变量的分布、差异、关联和异常特征。
- 从问题出发，寻找合适的统计量、模型或分析方法。
- 从统计图出发，选择观测值、分组或数据区间，研究其对结果的影响。
- 从统计量出发，追溯公式、计算过程与原始数据。
- 从公式出发，研究符号、运算、定义和推导关系。
- 从概念出发，探索相关定义、方法、模型和适用条件。
- 从损失函数或模型出发，改变分析目标，观察数学结果如何变化。

这些入口相互连接，但不构成固定的先后顺序。用户可以在任何位置停止、返回、切换方向或建立新的探索分支。

系统提供的是探索机会，而不是规定好的任务序列。

### 2.2 交互必须改变真实状态

StatLoom 中的交互不能停留在按钮点击、卡片展开或动画播放层面。每项核心操作都必须对应明确的对象、状态变化和结果反馈。

例如：

- 修改观测值，应更新所有受影响的统计量与图表。
- 调整分组，应重新计算与分组有关的统计结果。
- 选择公式项，应定位其对应的数学对象、计算依赖和数据来源。
- 切换损失函数，应重新计算目标函数及其相关结果，并显示适用的优化信息。
- 展开推导，应呈现真实的数学步骤、依据与前提，而不是只显示一段预先编排的解释。
- 选择概念关系，应展示关系的类型、方向、依据和适用条件。

界面不能使用独立维护的演示数字伪装实时计算，也不能通过没有实际意义的动画制造交互感。

### 2.3 完整能力与按需呈现

StatLoom 应保持完整的数学追踪能力，但不要求所有信息同时出现在主界面。

默认界面只展示当前任务所需的核心内容。用户可以通过悬停、点击、展开、次级菜单和可折叠面板，逐层进入更详细的信息。

信息按需呈现不意味着简化底层数学关系，也不意味着省略追踪结构。它只改变信息的展示时机和方式，不削减系统能够提供的解释深度。

### 2.4 引导是环境的一部分，而不是独立的教学流程

StatLoom 借鉴 Minecraft 的环境式引导思路：通过可操作对象、真实机制反馈、适时提示和知识资源，让用户在探索过程中逐渐理解系统。

引导主要承担三项职责：

1. 帮助用户发现界面中可以操作的对象。
2. 帮助用户理解当前操作产生的变化。
3. 为用户提供继续追踪或深入研究的入口。

提示必须简短、情境相关、可忽略、可关闭。探索建议可以提供方向，但不能被设计成必须执行的下一步。系统不通过经验值、等级、打卡、操作次数或里程碑衡量学习过程。

## 三、总体架构

StatLoom 由数学与数据基础层、交互状态与探索层、界面呈现层和分布式引导层构成。

### 3.1 数学与数据基础层

负责维护系统中真实存在的数据和数学关系。

主要职责包括：

- 用户数据导入、变量组织与数据检查。
- 数据对象、分组、筛选条件和分析配置管理。
- 统计计算、参数更新与结果重算。
- 数学对象、公式结构、符号映射和计算依赖维护。
- 统计量与数据来源之间的映射。
- 数学定义、理论推导、前提条件和适用范围管理。
- 损失函数表达式解析、数值计算与优化能力支持。

这一层不依赖具体图表、面板或动画实现。任何可视化结果都必须能够回到这一层找到对应的对象和计算依据。

### 3.2 交互状态与探索层

负责协调用户操作、数学对象、计算结果和探索上下文。

主要职责包括：

- 处理选择、编辑、拖动、筛选、分组和参数调整。
- 协调数据、公式、统计量和概念之间的联动。
- 管理当前选中对象、追踪路径和展开状态。
- 支持探索分支、撤销、重做、返回和分析状态恢复。
- 管理不同分析方法、损失函数和参数配置。
- 为界面提供统一的状态与对象查询接口。

这一层的核心原则是：所有呈现同一个数学对象的界面都应共享一致的状态，而不是各自保存互不关联的结果。

### 3.3 界面呈现层

负责将数学对象和交互状态转换成可操作的视觉结构。

主要组成包括：

- 数据表与数据分布视图。
- 公式、符号和计算过程视图。
- 统计量及其组成项视图。
- 概念关系网络。
- 可展开的推导面板。
- 损失函数探索画布。
- 对象检查器、次级菜单和知识卡片。
- 操作反馈、状态提示和导航控件。

布局由当前任务决定，而不是要求所有模块始终以固定的列或面板形式出现。

### 3.4 分布式引导层

负责在适当位置提供操作提示、描述性观察、探索建议、知识解释和外部资料。

引导层读取当前数据、选中对象、分析状态和用户操作情境，但不控制用户必须执行的顺序。

它可以提供下一种可能的操作，却不能将其定义为用户必须完成的下一步。

## 四、交互设计方法：借鉴 Terra Faction UI

StatLoom 应借鉴 Terra Faction UI 对交互语法的系统化处理，而不是只移植其色彩、材质和阵营风格。

### 4.1 交互由对象、动作、状态和反馈构成

每种核心交互都应明确四个要素：

1. **对象：** 用户正在操作什么。
2. **动作：** 用户可以对它执行什么操作。
3. **状态：** 操作前后，哪些数据或界面状态发生变化。
4. **反馈：** 系统如何让用户理解变化及其影响。

例如，用户选择一个数据点：

- 对象是具有唯一标识的观测值。
- 动作可以是查看、编辑、定位或调整其所属分组。
- 状态变化可能涉及观测值、分组关系以及相关计算结果。
- 反馈包括数据点的选中状态、相关统计量的更新，以及可供继续追踪的入口。

控件的外观、交互反馈和实际作用必须保持一致。一个看起来可拖动的对象应当真的支持拖动；一个看起来可展开的公式项应当展示与其对应的内容；一个显示为已完成的操作必须具有真实的完成状态。

### 4.2 每种对象建立自己的交互语法

不同的数学对象具有不同的操作方式，不应使用完全相同的交互模式。

| 对象类型 | 主要交互 | 预期反馈 |
|---|---|---|
| 数据点 | 选中、查看、编辑、定位、调整分组 | 数据值及相关计算结果更新 |
| 数据变量 | 选择、筛选、切换显示、查看类型 | 关联数据视图与分析结果更新 |
| 统计图 | 框选、缩放、比较、切换维度 | 选区与数据、统计量保持联动 |
| 统计量 | 展开、查看贡献、反向追踪 | 显示组成项、中间计算和原始数据 |
| 公式项 | 选中、展开、查看定义、追踪依赖 | 关联符号、计算结果和数据对象高亮 |
| 推导步骤 | 展开、折叠、继续追踪、切换分支 | 显示对应依据、前提和关联对象 |
| 概念节点 | 查看定义、探索关系、进入推导 | 展示关系类型及可继续探索的方向 |
| 损失函数 | 编辑表达式、切换目标、调整参数 | 更新损失曲线、数值结果和优化信息 |
| 分析配置 | 修改方法、参数和筛选条件 | 更新受影响的分析结果并保留配置 |

交互语法应随着数学对象的扩展而扩展。新增统计方法时，应尽可能复用现有的选择、追踪、反馈和状态管理机制，而不是为每种方法重新设计一套互不兼容的交互体系。

### 4.3 控件状态必须清晰

所有交互控件都应根据真实状态呈现相应反馈。

至少需要区分：

- 默认状态。
- 悬停状态。
- 选中状态。
- 键盘焦点状态。
- 正在编辑状态。
- 操作成功或完成状态。
- 无效输入或操作失败状态。
- 暂时不可用状态。

不同状态不应只依赖颜色区分，还可以通过边界、形态、图标、文字或位置变化进行表达。

所有关键操作都应支持清晰的键盘焦点。非必要动效应支持减弱或关闭，关闭动效后，用户仍然能够辨认当前状态和操作结果。

### 4.4 动效服务于真实状态变化

动效可以帮助用户理解对象之间的变化关系，但不能替代真实计算。

例如：

- 数据点移动时，可以同步显示相关统计量的变化。
- 公式项被选中时，可以高亮对应的数据贡献。
- 展开推导时，可以显示新增步骤与原公式的关系。
- 切换损失函数时，可以平滑呈现目标曲线和最优解的变化。
- 追踪到原始数据时，可以突出对应观测值及其所属组。

纯符号推导不必强行配合数据动画；不存在真实动态过程的状态变化，也不应被伪装成实时计算。

## 五、工作台布局与信息组织

### 5.1 稳定框架与动态主体

StatLoom 采用稳定的工作台框架，内部主体区域则根据用户当前探索的对象与任务调整。

稳定框架负责：

- 当前数据集和分析上下文。
- 数据与对象入口。
- 当前选择和分析配置。
- 撤销、重做及返回。
- 当前探索路径和辅助面板的基本控制。

动态主体负责呈现当前主要任务，例如数据分布、公式推导、损失函数或概念网络。

辅助区域根据需要展开，承载对象详情、计算过程、概念解释和适用条件。

不要求所有区域始终可见，也不要求所有功能都隐藏在多级菜单中。核心对象和常用操作应当容易发现，详细信息则可以按需展开。

### 5.2 布局由任务决定

不同任务可以采用不同的布局：

- 数据探索时，数据表和分布图可以并排显示。
- 追踪统计量时，公式与数据贡献可以并排呈现。
- 阅读推导时，公式和步骤成为主体，原始分析状态仍然保留。
- 探索损失函数时，表达式、目标曲线和优化结果成为主要区域。
- 浏览概念网络时，关系图成为主体，所选概念的定义与依据可以在辅助区域展开。

这些布局应共享相同的数学对象和分析状态。布局变化不能导致对象身份丢失、数据重新初始化或计算结果不一致。

### 5.3 信息按需揭示

主界面优先展示当前任务所需的内容。

具体数值、公式项、数据点、概念节点和状态标记可以通过悬停、点击或次级菜单进一步展开。信息层级应保持一致：

1. 核心对象及其当前结果。
2. 对象的直接组成、操作和依赖。
3. 详细计算过程、定义与推导。
4. 理论前提、适用条件、常见误解和参考资料。

用户可以直接进入较深层级，不必从第一层依次阅读。信息分层是展示策略，不是学习流程。

## 六、统一的数学对象与追踪体系

数学追踪是 StatLoom 的基础能力，不能被简化为概念网络中的普通节点连接。

### 6.1 四个追踪层级

**数据对象级**

覆盖观测值、变量、分组、筛选结果、均值、预测值等对象。

**公式项级**

覆盖统计量的组成项及其贡献，例如平方和中的单个偏差项、组均值偏差项和惩罚项。

**符号与运算级**

覆盖变量、下标、求和、平方、偏差、函数、运算符及中间表达式。

**概念级**

连接统计量与数学定义、损失函数、估计方法、统计模型、推断条件及相关理论。

### 6.2 双向追踪路径

系统应支持：

- 数据点 → 变量 → 公式符号 → 运算 → 统计量。
- 统计量 → 组成项 → 中间计算 → 原始数据。
- 概念 → 数学定义 → 公式 → 数据实例。
- 公式符号 → 相关概念 → 其他公式。
- 损失函数 → 优化目标 → 数值解 → 对应的统计解释与理论条件。

追踪必须由真实对象映射和依赖关系支持，而不是仅凭名称相似或概念关联生成。

### 6.3 区分关系类型

数学对象之间的关系至少需要区分：

- **计算依赖：** 某个结果依赖哪些数据或中间结果。
- **公式组成：** 一个表达式由哪些项构成。
- **定义关系：** 某个统计量或概念由什么数学表达式定义。
- **理论推导：** 在明确前提下，从已有命题推导出的结论。
- **概念关联：** 两个概念之间存在相关性，但不一定能直接推导。
- **表示映射：** 某个数据对象或数学对象在图表、公式或其他视图中的呈现位置。
- **用户自定义关系：** 用户为组织自己的研究而添加的连接、注释或分组。

系统维护的数学关系与用户自定义组织方式必须明确区分。用户可以自由添加注释和关系，但不能因此让未经验证的关系被误认为系统证明的数学结论。

概念网络用于发现可能的探索路径，具有明确前提的推导链用于解释路径为什么成立。两者不能互相替代。

## 七、真实计算与分析状态管理

### 7.1 统一的计算状态

所有图表、公式、统计量和概念详情都应引用统一的数学对象与计算结果。

修改数据后，系统应识别受影响的计算依赖，并更新相应结果。界面组件不能各自维护一套互不关联的统计数字。

数学计算层负责数值正确性，数学语义层负责对象含义和关系，界面层负责交互与呈现。

如果计算暂时不可用、表达式无效或优化尚未完成，界面应如实显示状态，不得继续展示容易被误认为最新结果的旧数值。

### 7.2 数据与视图分离

用户导入的原始数据应与筛选视图、分组配置、编辑后的探索状态相区分。

调整分组、改变筛选条件或创建探索分支时，不应无意覆盖原始数据或破坏此前的分析配置。

用户可以在保留原始数据的基础上尝试新的分组、参数或分析方法，并随时回到原有状态。

### 7.3 撤销、重做与探索分支

自主探索要求操作具有可恢复性。

系统应支持：

- 撤销与重做数据和分析配置的修改。
- 恢复此前的选择、追踪路径和视图状态。
- 保留不同损失函数、参数或分析方法的配置。
- 创建并比较分析分支。
- 返回发起追踪的对象。
- 在关闭辅助面板后继续原有分析。

视图调整、导航操作和实际数据修改应被区别管理。缩放图表不应触发无关的统计重算；展开知识卡片也不应改变分析参数。

## 八、交互式推导与知识卡片

### 8.1 可交互推导

推导默认呈现起点、关键关系和目标结论。用户可以展开中间步骤，并从任意步骤进入新的探索方向。

每个推导步骤应包含：

- 当前公式或变换。
- 使用的定义、恒等式、前提或定理。
- 简短解释。
- 在适用时，对应当前数据的数值实例。
- 相关符号、统计量和数据对象的定位入口。
- 继续推导、反向追踪或进入其他概念的入口。

用户可以停留在任何步骤，也可以转向其他分支。系统不能将展开全部步骤作为理解或完成任务的要求。

同一个数学对象可以连接多个方向。例如，从平方损失出发，可以研究最优常数预测与样本均值的关系、最小二乘与回归模型的联系，以及平方损失与其他损失函数的区别。

每条推导路径都必须明确依据、前提和结论，不能仅凭概念相关性拼接出没有逻辑保障的推导链。

### 8.2 知识卡片

知识卡片应嵌入当前的分析上下文，并与具体公式、统计量、概念或方法关联。

内容可以包括：

- 直观解释。
- 数学定义。
- 公式与计算依据。
- 适用条件和限制。
- 常见误解。
- 相关概念与推导入口。
- 外部教材、论文或其他参考资料。

知识卡片采用分层展示。用户可以只看直观解释，也可以继续展开定义、推导和适用条件。

系统必须区分基于当前数据的计算结果、系统维护的数学解释、外部资料的观点，以及用户自己的注释。

访问外部资料后，应尽可能保留当前数据集、变量选择、公式位置、参数和视图状态，以便用户返回原有探索环境。

## 九、分布式引导机制

引导不集中在一个教学页面，也不以连续弹窗或任务列表推进，而是分布在对象、操作与知识之间。

### 9.1 操作提示

首次遇到某种交互时，在相关对象附近提示其用途。

例如：

- 数据点可以定位到原始数据。
- 统计量可以展开中间计算。
- 公式符号可以查看定义。
- 公式项可以高亮对应的数据贡献。
- 损失函数编辑器支持哪些表达式操作。

提示应简短、可关闭，不阻止用户继续操作，也不反复要求用户执行某个动作。

### 9.2 描述性观察

系统可以根据数据自动提供描述性标记，例如样本量、组均值、分布范围、缺失值和变量类型。

这些标记只提供观察机会，不应自动变成教学结论。

组均值不同不代表差异具有统计显著性；异常值不必然是错误数据；分布差异也不自动证明因果关系。

用户可以从标记进入对应数据、计算过程和相关概念。

### 9.3 情境化探索建议

系统可以依据当前对象和操作情境提供可选建议。

例如：

- 查看组间差异后，可以进一步比较组内变异。
- 查看平方损失时，可以探索其最优常数预测与样本均值的关系。
- 查看某个统计量时，可以查看其组成项及数据来源。
- 切换分析方法时，可以比较不同方法的前提和结果。

建议必须说明其探索价值，不要求用户接受，也不自动将用户带入下一阶段。

### 9.4 按需解释与外部资源

用户可以在当前对象附近查看定义、推导、适用条件和延伸阅读。详细知识始终可追踪，但不要求一次性显示。

外部资料用于补充和延伸，而不是取代系统内部的数学解释。用户返回工作台后，应能继续原有分析。

## 十、自定义损失函数与方法探索

自定义损失函数是 StatLoom 的进阶能力。它的目标是帮助用户探索分析目标如何影响统计方法，而不是仅提供一个输入表达式并输出数字的计算器。

系统可以支持：

1. 常见损失函数及其参数。
2. 用户组合表达式、误差项和惩罚项。
3. 损失曲线、数值优化和结果比较。
4. 相关统计解释与理论条件的追踪。

系统必须区分三种能力：

- **表达式可计算性：** 表达式是否能够被安全解析和求值。
- **数值优化能力：** 当前算法能否在指定条件下寻找数值解。
- **理论保证：** 是否有明确的数学依据支持全局最优、唯一性或其他性质。

数值算法收敛不等于已经证明全局最优；某项理论性质尚未验证，也不等于该性质不存在。

例如，在固定数据、无约束常数预测条件下，平方损失的唯一全局最优解是样本均值；绝对损失的最优解对应样本中位数，偶数样本时中间两个有序观测值之间的整个区间都可能最优。

系统应将这些结论与相应前提一起展示，而不是无条件推广。

统计推断和方法导航也应保留，作为用户需要时可以调用的概念与分析工具。描述性分析优先，推断能力按需展开，不将统计方法选择变成强制的教学流程。

## 十一、视觉与技术实现原则

### 11.1 视觉设计

项目采用 Terra Faction UI 的设计与交互方法作为基础，并根据 StatLoom 的数学探索任务进行改造。

需要建立统一的设计令牌、布局规则、交互规范、状态反馈规范和动效规范。

视觉设计应突出数据分布、公式结构、统计量和概念关系，而不是用大量装饰性仪表、虚构读数或无意义的科幻效果营造复杂感。

色彩、边界、图标、形态和动效应帮助用户辨认对象类型、交互状态和关系类型。视觉差异必须具有信息职责。

### 11.2 技术架构

可采用 React 与 TypeScript 构建交互界面，D3 用于数据可视化，KaTeX 用于公式排版，Zustand 用于工作台状态管理。

建议将实现划分为：

- 数据与领域对象模块。
- 数学对象和公式结构模块。
- 统计计算与依赖更新模块。
- 数学追踪与理论推导模块。
- 工作台状态、历史操作和分析分支模块。
- 图表、公式、损失函数和概念网络的呈现模块。
- 引导、知识卡片与外部资料模块。

数学计算、语义关系和界面渲染必须相互解耦。不能依赖图形节点的位置来定义数学关系，也不能通过解析渲染后的公式字符串猜测数学含义。

二维交互优先，用于验证对象选择、计算联动、追踪、撤销与状态恢复。三维呈现作为后续探索方向，通过小型原型评估其是否确实提升空间关系的理解，而不是预先成为系统架构的必要条件。

数据集共享站可以作为后期独立服务，不应成为工作台核心能力开发的前置依赖。

## 十二、设计原则与禁止事项

### 12.1 核心原则

1. 用户可以从任意可用入口开始探索。
2. 每项核心交互都对应真实对象、状态变化和反馈。
3. 计算结果必须来自真实计算与明确的数学关系。
4. 完整数学追踪能力始终存在，但不要求一次性展示。
5. 系统可以提供建议，但不规定用户的探索顺序。
6. 操作发生不等于理解发生；系统提供继续检查与追踪的途径。
7. 数据修改、分析配置和视图状态应被区分，并尽可能支持恢复。
8. 计算结果、数值优化、理论推导、统计推断与因果解释必须明确区分。
9. 系统关系与用户自定义关系必须明确区分。
10. 数学语义、计算逻辑与可视化实现相互解耦。
11. 界面复杂度由真实任务决定，不以面板数量和视觉装饰衡量。
12. 不使用经验值、等级、打卡、里程碑或操作次数替代真实探索价值。

### 12.2 禁止事项

- 不将可执行操作组成必须完成的线性流程。
- 不把探索建议设计成必须执行的下一步。
- 不使用没有实际状态变化的按钮、动画或虚构数值伪装交互。
- 不因按需展示而删减底层数学追踪能力。
- 不将概念关联冒充为数学推导。
- 不将描述性差异直接解释为统计显著性或因果关系。
- 不将异常值自动标记为错误数据。
- 不将知识卡片退化为与当前分析无关的静态百科。
- 不将数值优化的结果直接视为理论保证。
- 不允许不同面板分别维护互不一致的统计结果。
- 不为了追求三维效果而牺牲对象操作、公式可读性和状态追踪。
- 不以视觉复杂度替代数学正确性与交互完整性。

## 十三、原型路线与验收标准

### 13.1 原型目标

原型的目标不是展示所有统计方法，而是验证 StatLoom 的核心交互语法是否成立：用户能否自由进入，操作真实对象，观察数学变化，追踪计算原因，并自主转向新的探索方向。

### 13.2 首轮原型功能

首轮优先实现：

1. 用户数据导入与编辑。
2. 数据表、变量和分组分布视图。
3. 可交互的数据点与选区。
4. 实时更新的统计量。
5. 公式项与原始数据之间的双向追踪。
6. 可展开、可分支、可反向追踪的推导面板。
7. 与当前对象关联的知识卡片。
8. 可切换损失函数的探索画布。
9. 分析配置的保存、撤销、重做与比较。
10. 可忽略的操作提示与情境化探索建议。

不将预测—验证任务作为原型的必需模块，也不要求用户走完预定流程。

### 13.3 验证场景

使用一份由用户导入、包含分组变量与数值变量的数据集作为测试对象。

用户可以从数据分布开始，也可以直接选择某个统计量或公式。

当用户修改一个观测值时，系统更新相关组均值、偏差和平方和；用户可以从结果进入公式项，查看计算贡献并定位到原始数据。

用户也可以直接打开组间平方和的定义，追踪组均值与总体均值的关系，或从相关公式进入损失函数画布，比较平方损失与绝对损失的优化结果。

上述行为只是可自由选择的探索方向，不构成规定的操作顺序。用户可以随时停止、撤销、返回或建立新的分析分支。

### 13.4 验收标准

原型应通过以下检查：

- 用户无需完成教程即可找到可操作对象。
- 修改数据后，所有受影响的计算结果正确更新。
- 公式、统计量和原始数据之间可以双向追踪。
- 追踪关系有明确类型、依据和适用条件。
- 推导可以停留、展开、分支和返回。
- 切换分析方法或损失函数时，原有配置可以保留和比较。
- 关闭知识卡片或辅助面板后，当前分析状态不丢失。
- 提示与建议可以忽略或关闭，不会强迫用户进入下一步。
- 界面状态与真实计算保持一致。
- 描述性统计、统计推断、优化结果与因果解释得到明确区分。
- 键盘焦点、必要的无障碍状态和减弱动效模式得到支持。

## 十四、项目的最终目标

StatLoom 的核心竞争力不在于提供更多统计学知识卡片，也不在于让用户完成更多操作，而在于建立一个真正可探索的统计学环境。

用户可以从自己的数据出发，也可以从一个公式或概念开始；可以先操作再追踪，也可以先查看理论依据再回到数据；可以随时切换方向，而不必遵循系统预设的学习顺序。

Terra Faction UI 提供的是设计规则、交互语法、状态反馈与任务布局的方法。StatLoom 则在此基础上建立数学对象与真实计算之间的统一关系，使每次操作都有可理解的后果，每个结果都可以追溯，每个概念都能在适当条件下连接到公式、数据与理论。

**StatLoom 的目标不是告诉用户下一步应该学什么，而是让用户在任何一步都有继续探索的可能。**
